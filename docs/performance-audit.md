# V: performance, memory and correctness audit

2 November 2026. Audited build: V 4.0 (4.0.0) from `build.sh`, installed in `/Applications/V.app`.
Toolchain: Swift 6.4.2, macOS 26.6.2. Machine: Apple M4 with 16 GB of memory.

## Summary

V launches quickly and uses no CPU when idle. Its image pipeline, however, has no memory bound and does
more decoding work than the screen needs:

1. **Memory grows without limit while browsing (critical).** The full-size cache is trimmed only when a
   photo has to be decoded from scratch. Moving to a photo that is already preloaded never trims it.
   That happens at a normal reading pace and every time the slideshow advances, so every photo passed
   stays in memory. Measured: +183 MB per 24 MP photo, and 2.3 GB after 12 photos. A slideshow of a
   camera folder ends in swapping.
2. **Holding an arrow key starts many full-size decodes at once.** The load queue is concurrent, and
   nothing is cancelled before it starts. Holding → for one second peaked at 1.0–5.7 GB, with up to
   28 threads and 2.4–6.4 s of CPU.
3. **Every photo is decoded at full resolution, whatever the screen.** A 24 MP photo holds 92 MB
   (183 MB once shown) and a 48 MP HEIC holds 186 MB, and each decode briefly needs about three times
   that. Photos stored sideways take 2–4× longer, because the full-size image is rotated on the CPU.
   Sideways storage (EXIF orientation 6) is how most phones and cameras save portrait shots.
4. **The folder is listed on the main thread before anything appears.** Opening one photo in a
   10,000-photo folder blocked the main thread for 342–375 ms.

A prototype of the first three fixes changed about 20 lines (appendix A). With it, browsing memory
stayed flat at 66–90 MB instead of growing to 2.3 GB. The key-repeat peak fell from ~1.1 GB to
161 MB, and a sideways photo became sharp in 65 ms instead of 189 ms.

| Real viewer code, 2560×1600 @1x screen | Today | Prototype (appendix A) | Target after all fixes |
|---|---|---|---|
| Open 24 MP JPEG: show → sharp photo | 79–134 ms | 58–71 ms | ≤ 70 ms |
| Open sideways 24 MP JPEG (EXIF 6) | 189–266 ms | 65 ms | ≤ 75 ms |
| Open 48 MP HEIC | 113–139 ms | 107 ms | ≤ 80 ms |
| Footprint 1 s after opening a 24 MP JPEG (neighbours preloaded) | 296 MB (peak 568) | 66 MB (peak 155) | ≤ 100 MB |
| Footprint 1 s after opening a 48 MP HEIC | 605 MB | 168 MB | ≤ 100 MB |
| Browsing: → every 0.7 s, 12 times | 294 → 2,312 MB, 13 photos held | flat 66–90 MB, 2–3 held | flat ≤ 150 MB |
| Holding → for 1 s (24 MP JPEG) | peak 1.0–5.7 GB, 8–28 threads, 2.4–6.4 s CPU | peak 161 MB, 8 threads, 0.7 s CPU | peak ≤ 250 MB |
| Holding → for 1 s (48 MP HEIC) | peak 1.2–1.8 GB, settles at 777 MB | peak 216 MB, settles at 163 MB | peak ≤ 250 MB |
| Open a photo in a 10,000-photo folder: main thread blocked | 342–375 ms | unchanged | ≤ 20 ms |

## How this was measured

- **Photos.** Synthetic photos, generated by `tools/perf/gen.swift` and free of personal data:
  - 24 JPEGs at 24 MP (6000×4000, 7 MB each, with an EXIF thumbnail). Every sixth one is stored
    sideways (orientation 6), plus one `.svg` file.
  - Four HEICs at 48 MP (8064×6048).
  - Six 5K PNG screenshots, with no embedded thumbnail.
  - A 60-frame GIF at 800×600.
  - A 10,000-photo folder made of hard links.
- **Decode strategies.** `tools/perf/bench.swift` runs each measurement in a fresh process, to get a
  clean peak footprint. Times are the median of 5 runs, with a warm disk cache.
- **The app itself.** `tools/perf/harness/main.swift` compiles the real `Sources/` with the same
  flags as `build.sh` and drives `ViewerWindowController` through its non-private API. The window is
  fully transparent and click-through, and the app never activates. Footprint is
  `task_vm_info.phys_footprint`, which is what Activity Monitor shows as Memory.
- **Everything at once.** `tools/perf/run.sh` runs all of the above. Appendix B explains how.
- **Screen.** This session ran over Jump Desktop: one 2560×1600 display at 1× scale and 30 Hz. On a
  Retina display the fitted photo is larger, so the decode savings for 24 MP photos are smaller (see H2).

## Findings

Severity reflects user impact: **Critical** means it can take the Mac down, **High** means it is
clearly felt, **Medium** means it is wasteful or felt in edge cases, and **Low** means polish or
hygiene. Line numbers refer to the audited sources.

### C1 · Critical: the full-size cache grows without limit

`Sources/ViewerWindowController.swift`. `trimCache()` (337) is called only in the slow path of
`display()`, after a fresh decode (317). These paths add photos to the cache but never trim it:

- the fast path, where the photo is already cached (302–306);
- preload completion (342–352).

At reading pace or in a slideshow, the next photo has always finished preloading, so every
navigation takes the fast path. Every photo passed stays cached at full resolution.

- **Evidence.** Pressing → every 0.7 s held 2, 3, 4 … 13 photos. Footprint went from 294 to 2,312 MB
  after 12 steps (`tools/perf/run.sh`, "pace"), and nothing stops it. Once a photo has been on screen
  it costs about twice its decoded size: +183 MB per 24 MP photo, most likely the decoded pixels plus
  Core Animation's converted copy, which lives as long as the `CGImage`.
- **Fix.**
  - Trim on every path: navigation, preload completion, folder change and trash.
  - Keep only the current photo and its two neighbours (see the pipeline below).
  - Add a `DispatchSource.makeMemoryPressureSource` handler: on `.warning`, drop the neighbours and the
    full-resolution tier; on `.critical`, also clear the thumbnails.

### H1 · High: decode work is unbounded and duplicated

`loadQueue` (32) is a concurrent `DispatchQueue`. Each `display()` of an uncached photo queues a
full-size decode (311). The generation check runs only after the decode finishes (314), so a
key repeat at 30 Hz queues 30 decodes, and GCD spawns threads for them.

Every completed decode then calls `preloadNeighbors()`, which queues more work. `preloadNeighbors`
does not know which decodes are already in flight. Its completion also throws away a finished
decode when the user has meanwhile moved onto that photo (347), even though `display()` has already
started a second decode of the same file.

- **Evidence.** Holding → for one second gave:
  - peak 1.03–1.45 GB, 8–12 threads and 2.4–3.3 s of CPU (five runs);
  - peak 5.7 GB, 28 threads and 6.4 s of CPU in one run where the burst began 0.7 s after opening,
    with the peak still rising after the key was released;
  - for 48 MP HEICs, peak 1.2–1.8 GB, and afterwards all four photos of the folder were still held.
- **Fix.**
  - Use one `OperationQueue` with 1–2 concurrent operations.
  - Order the work: current photo first, then next, then previous.
  - Cancel queued work that is no longer the current photo or a neighbour, before it starts.
  - Track in-flight decodes by URL, so `display()` attaches to a running preload instead of starting
    another one.
  - While a key is held (navigations less than about 120 ms apart), show the thumbnail and decode only
    where the user stops.

### H2 · High: every photo is decoded at full resolution

`ImageLoader.fullImage` (`Sources/ImageLoader.swift`, 35–52) decodes at
`min(longSide, 12_000)` through the thumbnail API, with the EXIF transform. The screen never shows
more than the fitted size until the user zooms in. On this screen a 3:2 photo fits in 1941×1294 px.
On a 14-inch MacBook Pro it fits in about 2277×1518 px. A 5K display can show close to full size.

Decode cost per photo (`tools/perf/bench.swift`, one process each; "peak" is the transient extra
memory during the decode):

| Photo | Today: full size + transform | Thumbnail API at full ÷ 2ᵏ, transform | `CreateImageAtIndex`, subsample factor 2, no transform |
|---|---|---|---|
| 24 MP JPEG | 67–88 ms · 92 MB · peak +279 MB | 33–38 ms · 23 MB · peak +72 MB | 24–27 ms · 23 MB · peak +48 MB |
| 24 MP JPEG stored sideways | 183–333 ms · peak +279 MB | 48–60 ms · peak +73 MB | 24–25 ms · peak +48 MB |
| 48 MP HEIC | 106–111 ms · 186 MB · peak +203–392 MB | 54 ms at 2016 px · 11.6 MB · peak +23 MB | 62–74 ms at 4032 px · peak +105 MB |
| 5K PNG screenshot | 67–74 ms · 56 MB · peak +171 MB | 91–99 ms · 14 MB · peak +97 MB | 65–71 ms · 14 MB · peak +24 MB |

What the measurements show:

- **JPEG has a fast path only at exact power-of-two fractions.** ImageIO's JPEG decoder scales in the
  DCT domain only at ½, ¼ and ⅛. Asking for 3000 px from a 6000 px photo took 38 ms. Asking for
  3024 px fell off the fast path and took 104 ms, slower than a full decode.
- **The sideways penalty is the CPU rotation of the full-size bitmap,** +115 ms or more. Rotating
  the smaller screen-sized image costs 10–25 ms. Applying the orientation as a layer transform costs
  nothing.
- **HEIC is fast at any size.** Use the exact fitted size.
- **PNG gets no faster through the thumbnail API.** `kCGImageSourceSubsampleFactor` keeps the time
  and cuts the peak from 171 to 24 MB.
- **Full-size decodes also briefly need about 3× the image size.** Each concurrent decode in H1
  multiplies that.

Fix: decode two tiers per photo, as described in the pipeline below. Keep the trilinear minification
filter (`ImageCanvasView.swift:49`), because the screen tier can still be up to 2× larger than the
fitted size. The canvas lays out in full-resolution pixel units (`info.pixelSize`), so swapping in a
smaller texture does not change any zoom maths.

### H3 · High: the folder is listed on the main thread before anything is shown

`show(urls:)` calls `ImageLoader.browseList` synchronously (234), before `display()` starts the
decode (263).

- **Evidence.** In a 10,000-photo folder, `show(urls:)` blocked the main thread for 342–375 ms. The
  sharp photo arrived 415–459 ms after `show`, against about 80 ms in a small folder. The listing
  alone took 295 ms and briefly needed 101 MB. The cost broke down as:

  | Step | Time |
  |---|---|
  | `contentsOfDirectory` | 57 ms |
  | Filter | 23 ms |
  | `standardizedFileURL` on every item (`ImageLoader.swift:83`) | 63 ms |
  | Sort, which re-derives `lastPathComponent` on every comparison (84) and allocates about 80 MB of autoreleased strings | 150 ms |

  The same result with one `resourceValues` call per item, a `Set` of decodable types and
  precomputed sort keys took **72 ms and 15 MB**.
- **On a network or external disk** this is the dominant delay, and it scales with folder size.
- **Fix.**
  - Show the opened photo at once, with `files = [opened]`, and start its decode first.
  - List the folder off the main thread, then swap in the sorted list and recompute the index by URL.
  - Make the listing cheaper:
    - filter with `CGImageSourceCopyTypeIdentifiers()`, computed once;
    - precompute names before sorting;
    - find the start index by name instead of standardizing every URL.

### M1 · Medium: work that starts after the UI could start before it

Launch-to-sharp-photo is the user-facing number, because V quits when its window closes and every
double-click in Finder is a fresh launch. The time is spent in this order:

| Step | Time |
|---|---|
| Process start → run loop | 52–71 ms (350–500 ms on the first launch of a newly built binary) |
| Controller init (window, Auto Layout, stack views, SF Symbols) | 25–33 ms |
| Listing (H3) | 6–375 ms |
| Decode | 60–330 ms |

The steps run strictly one after another.

- **Fix.** Start the decode of the opened photo in `application(_:open:)`, before building the
  controller, so it overlaps the UI work. SF Symbols are only about 5 ms of the init, so they are not
  worth caching.

### M2 · Medium: file I/O on the main thread for every photo shown

- `ImageLoader.info` runs on the main thread in `display()` (277). It runs again on every rotate (467),
  only to refresh the label.
- On local SSD it costs 0.1–0.6 ms, but 7 ms for a 60-frame GIF, because `CGImageSourceGetCount`
  scans the whole file. On a network or external disk it is unbounded.
- `isAnimatableType` and the file-size lookup each add a `resourceValues` call. The cached values from
  the listing are lost because the URLs were re-standardized (H3).
- **Fix.**
  - Read `ImageInfo` on the decode queue and cache it per URL; the struct is tiny.
  - Check the UTType before counting frames.
  - Reuse the cached info in `rotate`.

### M3 · Medium: Copy can freeze the app on large photos

`copy(_:)` (480–493) runs everything on the main thread:

- for PNG, JPEG and TIFF it reads the whole file with `Data(contentsOf:)`;
- for everything else, such as HEIC, WebP and RAW, it decodes the photo through `NSImage` and builds an
  uncompressed TIFF. For a 48 MP HEIC that is about 190 MB, and seconds of spinning beach ball.

**Fix.** Put the file URL on the pasteboard at once. Provide image data lazily through
`NSPasteboardItemDataProvider`. Offer the original bytes under their own type (`public.heic` and so
on) rather than re-encoding them as TIFF.

### M4 · Medium: the thumbnail pipeline repeats work and holds more than it shows

- **Churn on every navigation.** `display()` calls `thumbQueue.cancelAllOperations()` and
  `thumbsLoading.removeAll()` each time (274–275). Thumbnails that were queued are dropped and queued
  again by the next filmstrip draw. Thumbnails in flight are forgotten and decoded again.
- **Wrong size.** Thumbnails are decoded at 160 px (361), but a slot is 56 pt: 112 px on Retina and
  56 px on this 1× screen.
- **Count-limited cache.** The cache allows 600 items (61), up to about 40–46 MB.
- **No cache across launches.** Formats without an embedded thumbnail, such as PNG, GIF, TIFF and
  WebP, cost a full decode per thumbnail, 74–79 ms each for a 5K PNG, on every launch.
  `QLThumbnailGenerator` returned the same thumbnail in 0.6–1 ms once cached, and that cache survives
  launches. Its first call took 87–114 ms.
- **Fix.**
  - Decode thumbnails at slot size.
  - Use `NSCache.totalCostLimit` in bytes (about 8 MB) instead of a count.
  - Cancel only requests whose slot scrolled out of view, and order the rest by distance from the
    current photo.
  - Consider QuickLook for formats without embedded thumbnails. Embedded JPEG and HEIC thumbnails
    already cost only 0.2 ms and 3 ms through ImageIO.

### L1 · Low: the filmstrip pop-in redraws the whole strip on the CPU at 60 Hz

`FilmstripView` animates by running a 60 Hz `Timer` (84) that marks the whole view dirty. `draw(_:)`
then re-fetches every slot's thumbnail (47) and redraws all of them with high-quality interpolation
(44).

- **Cost.** One draw takes 0.5–1.7 ms on the main thread, measured offscreen:

  | Strip | Slots | Time per draw |
  |---|---|---|
  | 2520 pt at 1× | 38 | 0.54 ms |
  | 1472 pt at 2× | 22 | 0.98 ms |
  | 2520 pt at 2× | 38 | 1.66 ms |

  That is 3–10 % of a core for the roughly 3 s that a 38-thumbnail cascade lasts, and it recurs
  whenever the strip scrolls.
- **Judder.** The timer is not synced to the display, which shows on 120 Hz ProMotion screens.
- **Fix.** Use one `CALayer` per slot, with the thumbnail as its contents and
  `minificationFilter = .trilinear`. Pop each in with a `CABasicAnimation` on `transform.scale` and
  `opacity`, staggered through `beginTime`. That removes the timer and `draw(_:)`.

### L2 · Low: pop-in state is keyed by index

`appearTimes` (17, 51–53) is keyed by position, never reset and never pruned. After opening another
folder or trashing a photo, thumbnails at reused positions skip the pop-in or play it for the wrong
photo. Key it by URL and reset it when `count` changes.

### L3 · Low: rotating while a photo loads is undone

`display()` captures `rotation` (289) and applies it when the decode lands without a thumbnail (321).
If the user rotates in between, the photo snaps back. The label, which reads `rotations[url]`, then
disagrees with the photo. Read `rotations[url]` at completion time.

### L4 · Low: SVG and Illustrator files are treated as photos

- **What is wrong.** `isImage` (`ImageLoader.swift:67`) accepts anything that conforms to
  `public.image`. That includes `public.svg-image` and `com.adobe.illustrator.ai-image`, which ImageIO
  cannot decode. It can decode 62 type identifiers, and these two are not among them.
- **What the user sees.** These files appear in the folder as blank filmstrip slots and show
  "Can’t open".
- **Where it is registered.**
  - `Info.plist` claims `public.image` at rank Default.
  - `DefaultViewer.imageTypes` adds `.image` (`AppDelegate.swift:135`), so after `--make-default`,
    double-clicking an `.svg` opens V.
- **Fix.** Filter and register only `CGImageSourceCopyTypeIdentifiers()` types. `public.avis`
  (AVIF sequences) is decodable but does not conform to `public.image`; add it if wanted.

### L5 · Low: launching from the Dock waits 0.4 s before the Open panel

`applicationDidFinishLaunching` waits 0.4 s (`AppDelegate.swift:11`), because it cannot tell whether a
document is on its way. AppKit delivers `application(_:open:)` before `applicationDidFinishLaunching`
when it launches with documents. Check `openedSomething` directly instead, or implement
`applicationShouldOpenUntitledFile(_:)` and `applicationOpenUntitledFile(_:)`. Verify with a Finder
double-click and a Dock launch.

### L6 · Low: opening a photo during the close animation quits the app

`closeViewer` sets `isClosing` and closes the window when the 0.15 s animation ends. A `show(urls:)`
in that window takes the already-visible branch (259–261), and the pending `window.close()` then fires. That
calls `onClose`, and the app terminates, dropping the photo the user just opened. Cancel the close
when `show` arrives: clear `isClosing`, remove the animations and restore alpha.

### L7 · Low: the slideshow lets the display sleep

The slideshow holds no power assertion, so the display can sleep or the screen saver can start
mid-show. The 4 s timer (534) also has no tolerance. Hold
`ProcessInfo.processInfo.beginActivity(options: [.idleDisplaySleepDisabled, .userInitiated], reason:)`
while it runs, and set `timer.tolerance` to about 0.1 s.

### L8 · Low: force unwrap of `NSScreen.main`

`ViewerWindowController.init` (47) crashes if there is no screen, which can happen briefly during
clamshell or display changes. Fall back gracefully.

### L9 · Low: build flags

- `build.sh` compiles without whole-module optimisation and does not strip symbols. Adding `-wmo`
  takes the arm64 slice from 314 KB to 297 KB, and `-Xlinker -dead_strip` plus `strip -x` takes it to
  232 KB. The runtime effect is negligible, but it costs nothing.
- The code compiles in Swift 6 language mode with 33 concurrency warnings and no errors:
  22 in `AppDelegate`, 10 in `ViewerWindowController` and 1 in `FilmstripView`. Most come from main-queue
  completions written as `DispatchQueue.main.async` or `OperationQueue.main.addOperation`. Mark the UI
  types `@MainActor` when touching them.

### L10 · Low: smaller items

- **Zoom keys disagree.** Bare `0` zooms to fit, but ⌘0 is Actual Size (`handleKey` 442, menu in
  `AppDelegate`). Pick one meaning.
- **No preload after some photos.** Neighbours are not preloaded after an animated image or a file
  that cannot be opened.
- **Busy work on every pan event.** `relayout` invalidates cursor rects and rewrites the zoom label on
  every drag or scroll event (`ImageCanvasView.swift:222–223`). Update the label only when its text
  changes, and invalidate cursor rects only when `canPan` changes or the drag ends.
- **Misleading count.** `--make-default` prints `imageTypes.count - failures.count` (`main.swift:6`),
  which mixes a type count with a count of error strings.
- **Unsupported mechanism.** `DefaultViewer.makeDefault` writes LaunchServices' secure plist directly
  and runs `killall lsd`. It works today, but Apple does not support it and it can break with any OS
  update. Keep it in mind, but don't change it as part of this work.
- **Icon catalog size.** The icon source is 1254×1254 px; Icon Composer expects 1024. `Assets.car` is
  2.3 MB, two-thirds of it flattened 1024 px renditions. This has no runtime cost.

## Recommended image pipeline

1. **Info.** Read `ImageInfo` off the main thread and cache it per URL. Count frames only for
   animatable types.
2. **Two tiers per photo:**
   - **Screen tier.** Decode the long side at `fullLong >> k`: the smallest power-of-two fraction that
     is still at least the fitted long side in device pixels (`fitZoom × max(pixelWidth, pixelHeight)`,
     from the canvas for the current screen and insets).
     - Simplest: the thumbnail API with `WithTransform` and `ShouldCacheImmediately`.
     - For PNG and TIFF: `kCGImageSourceSubsampleFactor`.
     - For HEIC: the exact fitted size is fine.
     - Optionally, later: apply EXIF orientation as a layer transform. That takes a sideways JPEG from
       48 ms to 25 ms, but the canvas must then handle mirrored orientations 2, 4, 5 and 7.
   - **Full tier.** Full resolution, requested only when `canvas.zoom` exceeds the screen tier's scale
     (`screenLong / fullLong`). Swap it in with `replaceContents` once it arrives. Drop it on navigation
     or on zooming back to fit. Re-decode the screen tier if the needed size grows, for example after
     moving to a larger screen or rotating a portrait photo.
3. **Cache.** Hold the screen tier for the current photo and its two neighbours only, and the full
   tier for the current photo only. Trim on every navigation. Use the memory-pressure handler from C1.
4. **Scheduler.** One `OperationQueue` with 1–2 concurrent operations:
   - the current photo at `.userInitiated`, ahead of the neighbours at `.utility`;
   - in-flight requests tracked by URL;
   - stale requests cancelled before they start;
   - key-repeat debounce (H1).
5. **Order of startup.** Decode the opened photo first, then build the UI, then list the folder off
   the main thread (M1, H3).
6. **Thumbnails and filmstrip.** Slot-sized thumbnails in a byte-limited cache, targeted cancellation,
   and a layer-based pop-in (M4, L1, L2).

## Verified fine

- **Idle.** At rest the app uses 0 % CPU and runs no timers.
- **Animated GIFs.** They play through `CGAnimateImageAtURLWithBlock` at about 12 % of one core and
  27 MB for 800×600 at 20 fps.
- **Launch.** Warm, it reaches the run loop in 52–71 ms. The controller builds in 25–33 ms, of which
  the 12 SF Symbols are about 5 ms.
- **Thumbnails.** Embedded EXIF thumbnails are already used: 0.2 ms for a JPEG, 3 ms for a HEIC.
- **Decoding.** Decodes run off the main thread with `ShouldCacheImmediately`, so drawing never
  decodes lazily. Generation checks keep stale photos off the screen.
- **Binary.** 674 KB universal, linking only system frameworks.

## Open decision: should V stay running after its window closes?

V quits when the viewer closes, so every Finder double-click pays for a launch. That is about 70 ms
to the run loop plus about 30 ms of UI on a warm machine, and 350–500 ms on the first launch after a
rebuild. If V stayed running with no Dock icon, reopening would skip both and keep decoder
caches warm. The cost is about 20–30 MB of idle memory, which macOS compresses when idle. The current
behaviour matches the "minimal memory" goal and Picasa's own viewer, so this audit recommends keeping
it unless reopen speed matters more to you. Either way, it is your call; the fix phases don't change it.

## Limits of this audit

- **Synthetic photos.** Real photos decode at similar speeds, but file sizes and embedded thumbnails
  vary. RAW files (develop cost) and network volumes were not measured. Expect the main-thread I/O
  findings (H3, M2) to matter more on slow disks.
- **Screen.** The only screen was a 1× 2560×1600 virtual display at 30 Hz. The 120 Hz claim in L1
  comes from the code, not from a measurement.
- **Filmstrip drawing.** AppKit drew the transparent harness window rarely, so filmstrip cost comes
  from the offscreen benchmark, not from the running app.
- **WindowServer and GPU memory** are outside V's footprint and were not measured.
- **The installed app was not launched,** because it covers the whole screen. The harness compiles the
  same sources with the same compiler flags.
- **Visual regressions** of the proposed changes need a manual check in the real app. This covers the
  open and close animations, sharpness at 100 %, the slideshow, trash and rotate.

## Appendix B: running the measurements

```bash
tools/perf/run.sh            # decode strategies and the real viewer code, about a minute and a half
tools/perf/run.sh decode     # only the ImageIO strategy table
tools/perf/run.sh app        # only the viewer scenarios
```

- **What each run does.** The tools are rebuilt from the current `Sources/` each time. Test photos,
  about 230 MB, are generated once into `$V_PERF_DIR`, which defaults to `$TMPDIR/v-perf`.
- **The scenarios:**

  | Scenario | What it does |
  |---|---|
  | `open` | Launch → sharp photo, then footprint once the neighbours are preloaded |
  | `launch` | As `open`, but built the way `AppDelegate` does it, decoding while the window is built |
  | `pace` | → every 0.7 s, 12 times |
  | `burst` | → at 30 Hz for 1 s, then 3 s to settle |
  | `zoom` | Actual size must show the photo's own pixels; zooming back to fit must release them |
  | `gif` | CPU and memory while an animated GIF plays |

- **Nothing shows on screen.** The window is fully transparent and click-through, and the process
  never activates.
- **"Photos held"** counts the controller's `[URL: CGImage]` cache through reflection. It reads "n/a"
  once the cache has a different shape.
